## Critical Gaps (must-have for production)

### Race-safe account number generation via PostgreSQL sequence

open_account() derives the sequence number from COUNT(LIKE pattern), which is not atomic. Two concurrent calls for the same branch+date see the same COUNT and generate the same account_number, producing an IntegrityError on the UNIQUE constraint with no retry logic. This makes the service non-production-safe under any real concurrency.

**Benchmarks:** Temenos T24, Oracle FLEXCUBE, Mambu

**Implementation notes:** 1. Add a PostgreSQL sequence in models.py: `sa.Sequence('cb_account_seq', start=1, increment=1)` and expose it via `sa.text("nextval('cb_account_seq')")`. 2. In services.py replace the COUNT query in open_account() with `seq = session.execute(sa.text("SELECT nextval('cb_account_seq')")).scalar_one()`. 3. Keep _generate_account_number(branch, seq) unchanged. The sequence is global (not per-branch-per-day) which is fine — uniqueness is the invariant, not contiguous day-branch numbering. 4. Alternatively use `INSERT … RETURNING` with a per-branch sequence table locked with `SELECT … FOR UPDATE SKIP LOCKED`. The PostgreSQL global sequence is simplest and sufficient.

### Channel enforcement in withdraw()

_assert_channel_allowed() is a stub (pass). BankProduct.allowed_channels is populated and indexed but completely ignored. A MOBILE-channel withdrawal on a BRANCH-only product succeeds silently. This violates product rules and creates regulatory/audit exposure.

**Benchmarks:** Temenos T24, Infosys Finacle, Oracle FLEXCUBE

**Implementation notes:** In services.py replace `_assert_channel_allowed` with: `def _assert_channel_allowed(self, account: Account, channel: str, session: Session) -> None:` then load `product = session.get(BankProduct, account.product_id)`. If `product.allowed_channels` is not None/empty and `channel not in product.allowed_channels`: raise `AccountStatusError(f'Channel {channel!r} not permitted for product {product.product_code!r}. Allowed: {product.allowed_channels}')`. Update the `withdraw()` call to pass `session` as well. Also apply the same check in `transfer()` for the from_account (channel defaults to ONLINE there).

---

### open_account: enforce min_opening_balance when deposit is zero

The min_opening_balance guard `if opening_deposit_cents < product.min_opening_balance_cents` is trivially False when both are 0, but a caller passing opening_deposit_cents=0 against a product with min_opening_balance_cents=5_000_000 will open an ACTIVE account with a zero balance, violating product rules.

**Benchmarks:** Temenos T24, Mambu, Finastra Essence

**Implementation notes:** In open_account() change the guard to: `if opening_deposit_cents < product.min_opening_balance_cents: raise CoreBankingError(...)`. This already fires correctly when deposit > 0 and below minimum. The bug is in the else branch: remove the unconditional `account.status = 'ACTIVE'` and replace it with a check — if `product.min_opening_balance_cents == 0: account.status = 'ACTIVE'` else `raise CoreBankingError(f'Product {product_code!r} requires a minimum opening deposit of {product.min_opening_balance_cents}c; got 0')`. Alternatively consolidate: move the guard to after account creation and before any branch, so it always fires regardless of the deposit value.

### Transaction reversal service method

LedgerEntry.reversal_of_id and transaction_type=REVERSAL are modelled but there is no CoreBankingService.reverse_transaction() method. Every production CBS requires the ability to reverse a posted entry (wrong amount, wrong account, operator error). Without this, corrections require hand-crafting entries outside the service, bypassing all business rules and audit guards.

**Benchmarks:** Temenos T24, Oracle FLEXCUBE, Thought Machine Vault Core, Infosys Finacle

**Implementation notes:** Add to services.py: `def reverse_transaction(self, session: Session, journal_id: str, reason: str, tenant_id: str = '', correlation_id: str = '') -> dict`. Logic: 1. Load all LedgerEntry rows for journal_id. Raise CoreBankingError if none found or any entry already has reversal_of_id set (prevent double-reversal). 2. Raise CoreBankingError if any entry.transaction_type is already REVERSAL. 3. For each entry: create a mirror entry with flipped entry_type (DEBIT↔CREDIT), same amount_cents, transaction_type='REVERSAL', reversal_of_id=entry.id, new journal_id, narrative=f'REVERSAL: {reason}'. Update account balances via _post_credit/_post_debit helpers. 4. Post GL reversal via _post_to_gl with reversed lines. 5. Emit new event cb.transaction.reversed (add to events.py). Return {reversal_journal_id, reversed_journal_id, entries_reversed}. Add new exception: `class TransactionAlreadyReversedError(CoreBankingError): pass`.

### Automated fee application service method

BankProduct.fees JSONB defines a full fee schedule (maintenance_fee_cents, transfer_fee_cents, atm_fee_cents, etc.) but no service method reads or applies these fees. LedgerEntry.is_fee and transaction_type=FEE exist but are never written. A bank cannot operate without automated fee posting — maintenance fees, transaction fees, and penalty fees are primary revenue items.

**Benchmarks:** Temenos T24, Oracle FLEXCUBE, Mambu, Infosys Finacle, Finastra Essence

**Implementation notes:** Add to services.py: `def charge_fee(self, session: Session, account_number: str, fee_type: str, override_amount_cents: int | None = None, reference: str = '', narrative: str | None = None, tenant_id: str = '', correlation_id: str = '') -> dict`. Logic: 1. Load account, assert not CLOSED. 2. Load product.fees JSONB; key lookup e.g. fees.get(f'{fee_type.lower()}_fee_cents', 0). 3. amount = override_amount_cents or product_fee. If 0, return early. 4. Check available_balance >= amount (InsufficientFundsError). 5. Call _post_debit(..., transaction_type='FEE', is_fee=True). 6. Post GL: DR CUSTOMER_DEPOSITS, CR FEE_INCOME. 7. Emit cb.fee.charged event. Return {journal_id, entry_id, fee_type, amount_cents, new_balance_cents}. Also add `def run_maintenance_fee_batch(self, session, fee_date: date, product_type: str | None = None, tenant_id: str = '') -> dict` that iterates ACTIVE accounts and calls charge_fee for maintenance_fee_cents. Add FeeChargedEvent to events.py.

### Automated hold expiry (EXPIRED status)

AccountHold.expires_at and status=EXPIRED are modelled but nothing ever expires holds. A PAYMENT_PENDING hold from a failed payment that was never explicitly released will permanently reduce available_balance, locking customer funds indefinitely. This is a fund-locking defect, not just a cosmetic gap.

**Benchmarks:** Temenos T24, Mambu, Oracle FLEXCUBE

**Implementation notes:** Add to services.py: `def expire_stale_holds(self, session: Session, tenant_id: str = '', correlation_id: str = '') -> dict`. Logic: 1. Query AccountHold where status='ACTIVE' AND expires_at IS NOT NULL AND expires_at < NOW(). Optionally filter by tenant_id. 2. For each hold: set hold.status = 'EXPIRED'; restore account.available_balance_cents += hold.amount_cents; account.holds_cents -= hold.amount_cents. 3. Emit cb.hold.expired (new event, similar to HoldReleasedEvent with release_reason='EXPIRED'). 4. Return {holds_expired, total_released_cents}. This method should be called from a scheduler (not yet present — see scheduler gap). Add HoldExpiredEvent to events.py.

### Tenant-configurable GL account codes

_CB_GL is a module-level constant dict. Multi-tenant deployments with different charts of accounts cannot override GL codes at runtime. In production, different legal entities or subsidiaries always have different GL structures. This blocks multi-tenant or multi-entity deployment.

**Benchmarks:** Temenos T24, Oracle FLEXCUBE, Infosys Finacle

**Implementation notes:** 1. Add a new model in models.py: `class GLAccountMapping(AuditMixin, Model): __tablename__ = 'cb_gl_mapping'; id, tenant_id (VARCHAR 64), cb_account_key (VARCHAR 50) — e.g. 'CASH_NOSTRO', gl_account_code (VARCHAR 20), description, is_active`. Unique constraint on (tenant_id, cb_account_key). 2. In CoreBankingService add `def _resolve_gl(self, session: Session, key: str, tenant_id: str) -> str`: query cb_gl_mapping for (tenant_id, key); fall back to _CB_GL[key] if not found (default chart). 3. Replace all `_CB_GL[key]` references in service methods with `self._resolve_gl(session, key, tenant_id)`. 4. Add GLAccountMappingView (ModelView) to views.py. 5. Add to register_models() in __init__.py.


## High Priority Gaps

### Interest calculation: AVERAGE_DAILY_BALANCE and FLAT methods

accrue_interest() always uses DAILY_BALANCE formula regardless of product.interest_calculation. Products seeded with FLAT (CON001 Consumer Loan) accrue daily using simple balance*rate/365, which is incorrect for a flat-rate loan. AVERAGE_DAILY_BALANCE cannot be computed without intraday balance history. Both calculation methods are customer-facing contractual terms.

**Benchmarks:** Temenos T24, Oracle FLEXCUBE, Mambu, Finastra Essence

**Implementation notes:** For FLAT calculation: the rate applies to the original principal, not the current balance. Add `original_principal_cents` to Account model (nullable, populated at loan disbursement). In accrue_interest(), add a dispatch: `if product.interest_calculation == 'FLAT': balance = account.original_principal_cents or account.current_balance_cents; elif product.interest_calculation == 'DAILY_BALANCE': balance = account.current_balance_cents; elif product.interest_calculation == 'AVERAGE_DAILY_BALANCE': balance = self._compute_avg_daily_balance(session, account, accrual_date)`. For AVERAGE_DAILY_BALANCE, add helper `_compute_avg_daily_balance(session, account, for_date) -> int` that sums balance_after_cents of CREDIT entries and uses opening balance to reconstruct weighted average. This requires querying LedgerEntry for that date, which is available. Add original_principal_cents Column(BigInteger, nullable=True) to Account in models.py.

### AML transaction monitoring integration point

No AML screening is performed at any point in the transaction flow. World-class CBS (Mambu via ComplyAdvantage, FLEXCUBE, Finacle) treat AML screening as a gate in the payment/transfer approval path. FinCEN BSA/AML and FATF requirements mandate transaction monitoring. Without this hook, the plugin cannot be used in any regulated jurisdiction.

**Benchmarks:** Mambu, Oracle FLEXCUBE, Infosys Finacle, Finastra Essence

**Implementation notes:** 1. Add a new model: `class AMLScreeningResult(AuditMixin, Model): __tablename__ = 'cb_aml_screening'; id, tenant_id, journal_id (FK cb_ledger_entry.journal_id, indexed), account_id (FK), screening_provider (VARCHAR 50), screening_ref (VARCHAR 100), risk_score (NUMERIC 5,2 nullable), status (VARCHAR 20: PASSED|FLAGGED|BLOCKED|PENDING), flagged_reason (TEXT nullable), screened_at (TIMESTAMPTZ), resolved_at (TIMESTAMPTZ nullable), resolved_by (UUID nullable)`. 2. In CoreBankingService add `def _run_aml_check(self, session, account, amount_cents, transaction_type, reference, tenant_id) -> None`: lazy-import an AML provider interface (e.g. `from pgappforge.plugins.fintech.aml.services import AMLService`); call `result = AMLService().screen_transaction(...)`. If status == BLOCKED: raise new `AMLBlockedError(CoreBankingError)`. If FLAGGED: create hold and emit cb.aml.flagged event. 3. Call _run_aml_check in deposit(), withdraw(), transfer() before posting entries. 4. Add AMLBlockedEvent, AMLFlaggedEvent to events.py.

### Scheduler registration for batch jobs (interest accrual, dormancy, hold expiry, maintenance fees)

accrue_interest(), run_dormancy_check(), expire_stale_holds(), and run_maintenance_fee_batch() are synchronous batch methods with no scheduler registration. They will never run autonomously. World-class CBS (all six benchmarks) run these as scheduled jobs. Without this, interest does not accrue, dormancy is never enforced, and holds never expire.

**Benchmarks:** Temenos T24, Oracle FLEXCUBE, Mambu, Infosys Finacle, Thought Machine Vault Core, Finastra Essence

**Implementation notes:** The project already has pgappforge/plugins/rules/scheduler.py. In __init__.py add a `register_schedules()` method to CoreBankingPlugin: use APScheduler (already likely in deps via rules plugin) to register: 1. `accrue_interest` — daily at 23:55 local time, cron trigger. 2. `run_dormancy_check` — daily at 02:00. 3. `expire_stale_holds` — every 15 minutes, interval trigger. 4. `run_maintenance_fee_batch` — monthly, first day, 01:00. Each job should get a DB session from the app context, call the service method, commit, and log the result. Wrap each in try/except to prevent one failure from blocking others. Add `CB_SCHEDULER_ENABLED: bool` config key (default True) to initialize().

The AccountView comment explicitly notes 'Deposit / Withdraw / Transfer / Freeze are separate BaseView routes below' but those routes do not exist. The admin UI cannot perform any financial transaction. This makes the entire UI component non-functional for operators.

**Benchmarks:** Temenos T24, Oracle FLEXCUBE, Infosys Finacle, Finastra Essence

All routes decorated with @has_access and permission 'can_cb_account_transact'. Register AccountActionsView in register_views() in __init__.py. ### AccountView: resolve customer_id and product_id to human-readable names

AccountView.list_columns shows 'customer_id' and 'product_id' as raw UUID strings. No select2_ajax_widget is wired. Operators cannot identify accounts by customer name or product name from the list view. This is a basic usability failure in any real deployment.

**Benchmarks:** Mambu, Oracle FLEXCUBE, Infosys Finacle

**Implementation notes:** In AccountView add `list_columns = ['account_number', 'customer_name', 'product_name', 'currency_code', 'current_balance_cents', 'available_balance_cents', 'status', 'opened_date']` using SQLAlchemy hybrid_property or related_views pattern. The cleanest approach for FAB: define `related_views` on AccountView pointing to the Party and BankProduct views, and use `column_formatters` to do a joined query. Alternatively add hybrid properties on Account: `@hybrid_property def customer_name(self): return self.customer.full_name if self.customer else str(self.customer_id)` (requires lazy-loading the Party relationship). Add `customer: Party = relationship('Party', foreign_keys=[customer_id], lazy='select')` to Account in models.py (Party is already in erp_party). For product_id use `product.product_name` via the existing product relationship. Update label_columns to match.

### IBAN generation and validation

Account.iban field exists (ISO 13616, UNIQUE) but no service method generates or validates IBANs. The field must be provided externally. For banks operating in SEPA or any jurisdiction requiring IBAN, this is not optional. IBAN generation is a deterministic function of bank code + branch + account number — it should be auto-populated at account opening.

**Benchmarks:** Temenos T24, Oracle FLEXCUBE, Finastra Essence, Thought Machine Vault Core

**Implementation notes:** Add to services.py: `def generate_iban(self, country_code: str, bank_code: str, branch_code: str, account_number: str) -> str`. Algorithm: 1. Build BBAN = bank_code + branch_code + account_number (zero-padded to fixed width per country rules). 2. Compute check digits via mod-97 on rearranged string (ISO 13616-1). Return f'{country_code}{check_digits:02d}{BBAN}'. 3. Add `def validate_iban(self, iban: str) -> bool` using the same mod-97 check. 4. In open_account(), if CB_AUTO_GENERATE_IBAN config key is True and country_code is set, call generate_iban() and populate account.iban. 5. Add CB_BANK_CODE, CB_COUNTRY_CODE, CB_AUTO_GENERATE_IBAN to config defaults in __init__.py. No external library needed — mod-97 is ~10 lines. Add IBANValidationError(CoreBankingError) for invalid IBANs passed externally.

### Statement delivery: PDF/CSV generation and email/SMS dispatch

AccountStatement.delivery_method (EMAIL/SMS/PRINT/PORTAL) and delivered_at are stored but generate_statement() leaves statement_url=NULL and no delivery logic exists. A statement that is never delivered to the customer is useless. This is a regulatory requirement in most jurisdictions (periodic statement delivery).

**Benchmarks:** Temenos T24, Oracle FLEXCUBE, Mambu, Infosys Finacle

**Implementation notes:** 1. Add `def render_statement_csv(self, session: Session, statement_id: str) -> str` that queries LedgerEntry rows for the statement period and returns a CSV string. 2. Add `def deliver_statement(self, session: Session, statement_id: str, tenant_id: str = '') -> AccountStatement` that: loads AccountStatement; calls render_statement_csv(); uploads to object storage via lazy-import of a StorageService (non-fatal on ImportError); sets statement_url; dispatches notification based on delivery_method via lazy-import of NotificationService; sets delivered_at = now(); flushes. Emit cb.statement.delivered event (add to events.py). 3. The generate_statement() method should optionally call deliver_statement() inline if `auto_deliver: bool = False` parameter is True. This keeps the existing contract (caller controls) while enabling automatic delivery.

### InterestAccrualDashboard /history route: implement actual data query

The /history endpoint renders a template with only a date_range_config widget and returns no accrual history records. This is a skeleton that provides zero value. Interest history is required for regulatory reporting, customer disputes, and auditor review.

**Benchmarks:** Temenos T24, Oracle FLEXCUBE, Infosys Finacle

**Implementation notes:** In views.py update InterestAccrualDashboard.history(): 1. Parse from_date and to_date from request.args (ISO format, default to last 30 days). 2. Query: `SELECT accrual_date, product_type (via join), COUNT(ia.id), SUM(accrued_cents), SUM(cumulative_accrued_cents) FROM cb_interest_accrual ia JOIN cb_account a ON ia.account_id=a.id JOIN cb_product p ON a.product_id=p.id WHERE ia.accrual_date BETWEEN from_date AND to_date AND (tenant_id filter) GROUP BY ia.accrual_date, p.product_type ORDER BY ia.accrual_date DESC`. 3. Pass rows list to template. 4. Add pagination (LIMIT 100 default). 5. Update interest_history.html template to render the data table with sortable columns.

### party.created subscription handler for customer onboarding

subscribe_to() returns ['party.created'] but no on_event() or handle_party_created() method exists in CoreBankingPlugin. Customer onboarding integration is declared but completely unimplemented. This means the cross-plugin event bus subscription is a no-op, and any downstream system depending on cb.account.opened being triggered after party creation will never receive it.

**Benchmarks:** Infosys Finacle, Mambu, Temenos T24

**Implementation notes:** In __init__.py add to CoreBankingPlugin: `def on_event(self, event_type: str, payload: dict, session=None) -> None`. Check `if event_type == 'party.created'`: extract customer_id from payload; look up the party's customer_type; if customer_type in ('INDIVIDUAL', 'SME', 'CORPORATE') and a default product is configured, optionally auto-open a default savings account using CoreBankingService().open_account() with product_code from config key `CB_AUTO_OPEN_PRODUCT` (default None = disabled). The handler must be non-fatal (wrap in try/except). This completes the declared subscribe_to() contract. Without a handler, the subscription registration misleads any event bus implementation that routes events to subscribed plugins.

### accrue_interest: fix tenant_id filter logic for empty string

The WHERE clause `Account.tenant_id == tenant_id if tenant_id else sa.true()` is a Python ternary embedded inside SQLAlchemy .where(). An empty string tenant_id ('') evaluates to falsy, bypassing the tenant filter and processing ALL tenants' accounts. In a multi-tenant system this is a data isolation breach: one tenant's interest run could process another tenant's accounts.

**Benchmarks:** Temenos T24, Oracle FLEXCUBE

**Implementation notes:** In services.py in accrue_interest() replace the inline ternary pattern with explicit conditional query building: `q = select(Account).join(BankProduct, ...).where(Account.status == 'ACTIVE')`. Then `if tenant_id: q = q.where(Account.tenant_id == tenant_id)`. Apply the same fix to the already_done_ids subquery for InterestAccrual.tenant_id. Audit all other service methods for the same ternary-in-where pattern — run_dormancy_check() already uses the correct `if tenant_id: q = q.where(...)` pattern. Only accrue_interest has the broken form.


## Medium Priority Gaps

### Per-account interest accrual events (not just batch aggregate)

InterestAccruedEvent is a single batch-level aggregate. Downstream consumers (loan systems, notifications engine, tax reporting) cannot react to a specific account's daily accrual without polling the database. World-class systems (Thought Machine, Mambu) emit per-account events for every financial posting.

**Benchmarks:** Thought Machine Vault Core, Mambu, Infosys Finacle

---

### Enforce relationship_manager_id as a proper FK

Account.relationship_manager_id is documented 'FK to Party (staff) — not enforced at DB level'. There is no ForeignKey constraint, no relationship(), and no validation. Saving an invalid UUID silently succeeds. RM assignment is a key CRM data point used for revenue attribution and customer service routing.

**Benchmarks:** Oracle FLEXCUBE, Infosys Finacle, Finastra Essence

---

### Intraday balance history table for AVERAGE_DAILY_BALANCE support

InterestAccrual stores only opening_balance_cents (balance at start of day). True AVERAGE_DAILY_BALANCE requires the time-weighted average of the balance across intraday postings. Without an intraday balance history table, ADB calculation must reconstruct balance from all LedgerEntry rows for the day — expensive at scale and fragile.

**Benchmarks:** Temenos T24, Oracle FLEXCUBE, Thought Machine Vault Core

---

### Islamic profit-sharing calculation (is_islamic flag)

BankProduct.is_islamic flag is stored but the service applies standard interest arithmetic regardless. Sharia-compliant products require Murabaha (cost-plus) or diminishing Musharakah (reducing partnership) profit-sharing logic, not riba (interest). This is legally required for any Islamic banking product.

**Benchmarks:** Temenos T24, Mambu, Finastra Essence, Oracle FLEXCUBE

---

### Balance sheet GL reconciliation — surface CB vs GL discrepancies

BalanceSheetView derives totals from cb_account.current_balance_cents (denormalised CB balances), not from the GL journal. Discrepancies between CB and GL (e.g. from failed GL posts, which are non-fatal) are never surfaced. Auditors and regulators require GL-derived balance sheet figures.

**Benchmarks:** Temenos T24, Oracle FLEXCUBE, Thought Machine Vault Core, Finastra Essence
