## Critical Gaps (must-have for production)

### Funds hold / balance check cycle missing

initiate_payment and validate_payment never verify that the debtor account has sufficient funds, and never place a hold on those funds. InsufficientFundsError is defined but never raised. hold_placed=False is hardcoded in PaymentValidatedEvent and PaymentCancelledEvent. This means a payment can be created and authorised against an account with zero balance, causing an overdraft at settlement time with no prior reservation. No world-class payments processor allows this; it is the #1 cause of settlement fails in naive implementations.

**Benchmarks:** Stripe, Adyen, Checkout.com, Rapyd, Flutterwave

**Implementation notes:** In services.py, inject CoreBankingService lazily at the top of validate_payment (after the PENDING guard). Use the existing CoreBankingService.place_hold(session, account_number, amount_cents + charges_cents, reason='PAYMENT_HOLD', reference=order.payment_reference, tenant_id=self._tenant_id). Store the returned hold.id in a new column py_payment_order.hold_id (UUID, nullable, no FK constraint needed). On cancel_payment, call CoreBankingService.release_hold(session, order.hold_id). On settle_payment, call CoreBankingService.withdraw() — the hold has already reduced available balance, so withdraw just converts the reserved amount to a settled debit. On reject_payment and return_payment, call release_hold. Add column to models.py: hold_id = Column(UUID(as_uuid=False), nullable=True, comment='AccountHold.id; released on cancel/reject/return'). Change PaymentValidatedEvent.hold_placed to True when a hold was placed. Raise InsufficientFundsError (already defined in services.py) when place_hold raises CoreBankingService.InsufficientFundsError.

### GL double-entry posting absent at every monetary event

settle_payment, reject_payment, receive_inbound_payment, and return_payment produce no GL journal entries. The clearing_reference and journal_id parameters flow only into domain events; the GL is never touched. This means the bank's books are never updated. No regulatory audit, no trial balance, no reconciliation is possible without GL postings. All world-class core banking systems (and the existing CoreBankingService._post_to_gl) treat this as non-negotiable.

**Benchmarks:** Stripe, Adyen, Checkout.com, Square, Rapyd

**Implementation notes:** Add a GL chart-of-accounts map near the top of services.py mirroring _CB_GL in core_banking/services.py: _PY_GL = {'NOSTRO': '1011', 'CUSTOMER_DEPOSITS': '2100', 'PAYMENT_SUSPENSE': '2110', 'FEE_INCOME': '4200', 'FX_GAIN_LOSS': '4300'}. In settle_payment, call GLService().post_simple_journal(lines=[{'account_code': _PY_GL['CUSTOMER_DEPOSITS'], 'debit_cents': order.equivalent_ksh_cents, 'credit_cents': 0, 'description': f'Payment settled {order.payment_reference}'}, {'account_code': _PY_GL['NOSTRO'], 'debit_cents': 0, 'credit_cents': order.equivalent_ksh_cents, 'description': f'Payment settled {order.payment_reference}'}], session=self._session, tenant_id=self._tenant_id, description=f'Payment {order.payment_reference}', source_doc_type='PaymentOrder', source_doc_id=str(order.id)). In receive_inbound_payment, reverse the entries: NOSTRO debit, CUSTOMER_DEPOSITS credit. In return_payment (new method, see gap below), post a reversal entry. Wrap each call in try/except GLServiceError — GL failure must be logged but non-fatal (same pattern as _emit). Use lazy import: from pgappforge.plugins.erp.finance.gl.services import GLService to avoid circular imports.

### return_payment service method and RETURNED flow entirely absent

PaymentOrder has returned_at column and RETURNED status. PaymentReturnedEvent is defined with return_reason_code and reversal_journal_id. No return_payment() service method exists. _RETURN_ALLOWED_FROM is not defined. The RETURNED status is unreachable through the service. Bank-to-bank payment returns are a routine operational reality on all rails (PESALINK, SWIFT, ACH), representing 1-3% of volume on any active rail.

**Benchmarks:** Stripe, Adyen, Checkout.com, Rapyd, Flutterwave

**Implementation notes:** Add to services.py: def return_payment(self, payment_order_id: str, *, return_reason_code: str, return_reason: str, actor_id: str = 'system') -> PaymentOrder. Status guard: order.status must be 'SETTLED' (raise PaymentImmutableError otherwise). Steps: (1) raw SQL UPDATE: status='RETURNED', returned_at=now(). (2) _append_status_event('SETTLED', 'RETURNED', actor_id=actor_id, notes=f'{return_reason_code}: {return_reason}'). (3) If order.hold_id is present, call CoreBankingService.release_hold() — in a return the funds come back. (4) Post GL reversal: debit NOSTRO, credit CUSTOMER_DEPOSITS (mirror of the original settle entry). (5) Emit PaymentReturnedEvent with reversal_journal_id from the GL post result. Add _RETURN_ALLOWED_FROM = frozenset({'SETTLED'}) at class level. Add return_payment to __all__ in services.py.

### Batch lifecycle incomplete — submit_batch, settle_batch, and process_clearing_response absent

Only create_batch and generate_pain001 are implemented. The batch status machine documents DRAFT→VALIDATED→AUTHORIZED→SUBMITTED→SETTLED but only DRAFT creation is reachable. BatchSubmittedEvent and BatchSettledEvent are defined but never emitted. No method ingests the clearing house acknowledgement (ACK/NAK) or settlement confirmation. ACH/EFT batch processing is a core operational loop in any bank; without submit and settle, batches are dead data.

**Benchmarks:** Stripe, Adyen, Rapyd, Flutterwave, Paystack

**Implementation notes:** Add three methods to services.py: (1) submit_batch(batch_id, *, actor_id='system') -> PaymentBatch: status guard DRAFT or VALIDATED→AUTHORIZED; set status='SUBMITTED', submitted_at=now(); call _get_rail_for_type(batch.batch_type) and raise RailNotAvailableError if None; emit BatchSubmittedEvent with batch_number, rail_code, total_payments, total_amount_cents, submitted_at. (2) settle_batch(batch_id, *, clearing_reference: str, accepted_ids: list[str], rejected_ids: list[str], actor_id: str = 'system') -> PaymentBatch: iterate accepted_ids calling settle_payment() on each; iterate rejected_ids calling reject_payment() with a generic BATCH_REJECT code; update batch: accepted_count, rejected_count, status='SETTLED' or 'PARTIALLY_SETTLED' or 'FAILED'; emit BatchSettledEvent or BatchPartiallySettledEvent accordingly. (3) process_clearing_response(batch_id, *, response_payload: dict) -> PaymentBatch: parse clearing house response dict (shape: {clearing_reference, accepted: [{payment_reference, uetr}], rejected: [{payment_reference, reason_code, reason}]}); call settle_batch() with the extracted lists.

### Transactional outbox table absent — events are fire-and-forget with no durability

All 18 events are emitted via _emit() which calls event_bus() in-process with no persistence. If the process crashes between session.commit() and the event_bus call, or if event_bus() raises, the event is permanently lost. There is no retry, no dead-letter, and no at-least-once delivery guarantee. Webhook reliability with at-least-once semantics is a Tier 1 requirement in every world-class system (Stripe, Adyen, Checkout.com all have durable outbox tables with exponential backoff retry).

**Benchmarks:** Stripe, Adyen, Checkout.com, Rapyd, Paystack

**Implementation notes:** Add a new model to models.py: class PaymentOutboxEvent(ImmutableRecordMixin, AuditMixin, Model): __tablename__ = 'py_payment_outbox'; fields: id (UUID PK), tenant_id (VARCHAR 64), event_type (VARCHAR 100 NOT NULL), payload (JSONB NOT NULL), idempotency_key (VARCHAR 100 UNIQUE NOT NULL — use payment_reference + event_type), status (VARCHAR 20 default 'PENDING': PENDING | DELIVERED | DEAD), attempts (INTEGER default 0), last_attempted_at (TIMESTAMPTZ nullable), next_retry_at (TIMESTAMPTZ default NOW()), delivered_at (TIMESTAMPTZ nullable). Add Index on (status, next_retry_at) and (tenant_id, idempotency_key). In PaymentsService._emit(), instead of calling event_bus() directly: INSERT an outbox row inside the same session.flush() that commits the business transaction (same DB transaction, so atomic). A background worker (APScheduler or Celery beat) polls py_payment_outbox WHERE status='PENDING' AND next_retry_at <= NOW() ORDER BY next_retry_at LIMIT 100 FOR UPDATE SKIP LOCKED, calls event_bus for each, marks DELIVERED or increments attempts with exponential backoff (next_retry_at = NOW() + interval '2^attempts minutes'). After 10 attempts mark DEAD. Register ImmutableRecordMixin on PaymentOutboxEvent (status updates use raw SQL UPDATE).

### AML compliance uses a stub — no rule evaluation, no structuring detection, no PEP check

_run_aml_check always returns False. The regulatory plugin has a fully implemented RegulatoryComplianceService.screen_transaction() and AMLRule/AMLAlert models (including THRESHOLD, VELOCITY, STRUCTURING rule types) but the payments service does not call them. This means every payment passes AML silently. AML transaction monitoring is a legal requirement under Kenya's Proceeds of Crime and Anti-Money Laundering Act (POCAMLA) and CBK AML guidelines, not optional.

**Benchmarks:** Stripe, Adyen, Checkout.com, Rapyd, Paystack

**Implementation notes:** Replace the stub _run_aml_check with: try: from pgappforge.plugins.fintech.regulatory.services import RegulatoryComplianceService; reg_svc = RegulatoryComplianceService(); result = reg_svc.screen_transaction({'amount_cents': order.amount_cents, 'payment_type': order.payment_type, 'creditor_name': order.creditor_name, 'debtor_account_id': str(order.debtor_account_id), 'currency_code': order.currency_code, 'channel': order.channel}, session=self._session, tenant_id=self._tenant_id); return result.get('flagged', False). Catch ImportError and log a warning (non-fatal pass-through). Also wire _run_sanctions_screen to RegulatoryComplianceService.screen_customer() rather than only checking creditor_name: pass both creditor_name and creditor_account_number. If aml_flagged is True, do not auto-raise — set the flag and let the authorizer decide, but add an AMLFlaggedError subclass for cases where rules are configured as AUTO_REJECT.

### Reference generation is not collision-safe under concurrency

_ref_seq uses random.choices(string.digits, k=6) — not a DB sequence. With 6 random digits there are 1,000,000 possible values per day. Under any meaningful load (100+ payments/second) birthday-paradox collisions become frequent. The UNIQUE constraint will catch collisions but the service has no retry logic — it simply propagates the IntegrityError to the caller, causing transaction aborts under load. All production payment systems use DB sequences (PostgreSQL SEQUENCE) for reference generation.

**Benchmarks:** Stripe, Adyen, Checkout.com, Rapyd

**Implementation notes:** In models.py, add one PostgreSQL sequence per reference type: sa.Sequence('py_payment_ref_seq', start=1, increment=1) and sa.Sequence('py_batch_ref_seq', start=1, increment=1) and sa.Sequence('py_so_ref_seq', start=1, increment=1). In services.py, replace _ref_seq with: def _next_ref(session, prefix, seq_name): nextval = session.execute(sa.text(f"SELECT nextval('{seq_name}')")).scalar(); return f"{prefix}-{date.today().strftime('%Y%m%d')}-{nextval:06d}". Call as _next_ref(self._session, 'PAY', 'py_payment_ref_seq'). This gives gapless, collision-free, human-readable references. The sequences must be created in a migration (CREATE SEQUENCE IF NOT EXISTS py_payment_ref_seq).


## High Priority Gaps

### Standing order scheduler absent — no automated execution of due orders

execute_standing_order() requires an external caller to invoke it manually. No scheduler, cron, or batch runner queries py_standing_order for next_execution_date <= today and triggers execution. SPECIFIC_DATES frequency is a no-op in _compute_next_execution_date (returns the same date, creating an infinite loop risk). pause_standing_order() and resume_standing_order() methods do not exist. EXPIRED status is never set even when end_date is passed. StandingOrderFailedEvent is defined but never emitted; total_failed is never incremented.

**Benchmarks:** Stripe, Adyen, Rapyd, Paystack

**Implementation notes:** Add scheduler.py to the payments plugin with a single function: def run_due_standing_orders(session: Session, tenant_id: str, event_bus=None, as_of_date: date | None = None) -> dict. It: (1) queries SELECT * FROM py_standing_order WHERE tenant_id=:t AND status='ACTIVE' AND next_execution_date <= :today FOR UPDATE SKIP LOCKED; (2) for each SO, calls svc.execute_standing_order() in a try/except; on failure: raw UPDATE total_failed = total_failed + 1; emit StandingOrderFailedEvent(failure_reason=str(exc), will_retry=True); (3) after each execution, if so.end_date and next_execution_date > end_date: raw UPDATE status='EXPIRED'; (4) returns {executed: N, failed: M}. Add to services.py: def pause_standing_order(so_id, *, paused_by) -> StandingOrder: guard status=='ACTIVE'; raw UPDATE status='PAUSED'; emit new StandingOrderPausedEvent. def resume_standing_order(so_id, *, resumed_by) -> StandingOrder: guard status=='PAUSED'; raw UPDATE status='ACTIVE'; emit StandingOrderResumedEvent. Fix _compute_next_execution_date for SPECIFIC_DATES: raise ValueError('SPECIFIC_DATES requires explicit next_execution_date update') to force callers to be intentional.

### Inbound payment does not credit the account or post to GL

receive_inbound_payment records a PaymentOrder in SETTLED status but never calls CoreBankingService to credit the beneficiary account balance, and never posts a GL entry. The journal_id parameter is accepted but placed only in the event payload. The account's current_balance_cents and available_balance_cents are never updated. This means inbound payments are ghost records that don't affect any account's actual balance.

**Benchmarks:** Stripe, Adyen, Checkout.com, Rapyd

**Implementation notes:** In receive_inbound_payment, after self._session.flush() for the PaymentOrder insert: (1) call CoreBankingService().deposit(session=self._session, account_number=creditor_account_number, amount_cents=amount_cents, description=f'Inbound {payment_type} from {debtor_name}', reference=ref, channel='CLEARING_HOUSE', tenant_id=self._tenant_id) — this posts both the LedgerEntry and the GL journal internally. (2) Capture the returned journal_id and put it in the emitted InboundPaymentReceivedEvent. Import CoreBankingService lazily (try/except ImportError). The creditor_account_id parameter should be renamed creditor_account_number to be consistent with CoreBankingService.deposit() which takes account_number, not account UUID — update both the signature and the model construction accordingly.

### FX conversion truncates instead of rounding — systematic understatement

equivalent_ksh_cents = int(amount_cents * exchange_rate) uses Python int() which truncates toward zero. On a USD 1,000 payment at a rate of 130.55, truncation gives 13,055,000 instead of the correct 13,055,000 — but at rates like 130.557 the error accumulates across thousands of transactions. The correct approach per ISO 4217 and every banking standard is ROUND_HALF_UP. Over a month of FX payments this produces a systematic reconciliation discrepancy that cannot be explained.

**Benchmarks:** Stripe, Adyen, Checkout.com

**Implementation notes:** In services.py initiate_payment: replace int(amount_cents * exchange_rate) with: from decimal import Decimal, ROUND_HALF_UP; rate = Decimal(str(exchange_rate)); equivalent_ksh = int((Decimal(amount_cents) * rate).quantize(Decimal('1'), rounding=ROUND_HALF_UP)). Apply the same pattern in receive_inbound_payment. Use Decimal(str(exchange_rate)) not Decimal(exchange_rate) to avoid float representation errors being promoted into Decimal. This one-line fix eliminates the systematic rounding error.

### PAIN.001 XML builder is not XML-safe and omits mandatory ISO 20022 elements

_build_pain001_xml uses Python f-string interpolation directly into XML. A creditor_name containing '&', '<', '>', or '"' produces malformed XML that any clearing house XML validator will reject. Missing mandatory elements per PAIN.001.001.03 XSD: PmtMtd (PaymentMethod), SvcLvl (ServiceLevel), LclInstrm (LocalInstrument), CdtrAgt (CreditorAgent BIC), DbtrAcct (DebtorAccount IBAN/BBAN), DbtrAgt (DebtorAgent BIC). The simplified output will be rejected by CBK/KEPSS and SWIFT validators.

**Benchmarks:** Adyen, Rapyd, Flutterwave

**Implementation notes:** In services.py _build_pain001_xml, replace f-string concatenation with xml.etree.ElementTree: import xml.etree.ElementTree as ET; root = ET.Element('Document', xmlns='urn:iso:std:iso:20022:tech:xsd:pain.001.001.03'); initn = ET.SubElement(root, 'CstmrCdtTrfInitn'). Use ET.SubElement() for all elements — ET automatically XML-escapes text via .text assignment. Add the missing mandatory elements: PmtMtd (hardcoded 'TRF'), SvcLvl/Cd ('NURG' for EFT, 'URGP' for RTGS), LclInstrm/Cd (rail_code), CdtrAgt/FinInstnId/BIC (creditor_bank_code if present), DbtrAcct/Id/Othr/Id (debtor_account_id), DbtrAgt/FinInstnId/BIC (bank's own BIC from config PY_BANK_BIC). Return ET.tostring(root, encoding='unicode', xml_declaration=True). Optionally add an lxml schema validation step if lxml is available (try: import lxml.etree; lxml.etree.fromstring(xml_bytes, lxml.etree.XMLSchema(pain001_xsd))).

### View cancel endpoint reads tenant_id from unvalidated form data — IDOR vulnerability

PaymentOrderView.cancel_order reads tenant_id from request.form with a default of 'default'. An authenticated operator on tenant A can POST tenant_id=tenant_B to cancel orders belonging to tenant B. This is a direct object reference vulnerability (OWASP A01:2021). Any multi-tenant deployment is exposed.

**Benchmarks:** Stripe, Adyen, Checkout.com

**Implementation notes:** In views.py PaymentOrderView.cancel_order, remove tenant_id from request.form. Instead derive it from the authenticated session: from pgappforge.security import current_user; tenant_id = getattr(current_user, 'tenant_id', None) or current_app.config.get('PY_DEFAULT_TENANT', 'default'). Also fix generate_pain001 in PaymentBatchView which has the identical pattern. The PaymentsService already enforces tenant_id on every query, but the view must not allow the caller to specify which tenant to operate as.

### View edit forms bypass service state machine for status fields

PaymentBatchView.edit_columns includes 'status' — operators can SET any batch status directly via the FAB edit form (e.g., set a DRAFT batch to SETTLED, skipping all validation). StandingOrderView.edit_columns includes 'status' with the same problem. This breaks the audit trail, never appends PaymentStatusEvent rows, and never emits domain events.

**Benchmarks:** Stripe, Adyen, Checkout.com

**Implementation notes:** In views.py, remove 'status' from PaymentBatchView.edit_columns and StandingOrderView.edit_columns. Add explicit action endpoints instead, following the pattern of PaymentOrderView.cancel_order: add @expose('/authorize/<pk>', methods=['POST']) def authorize_batch(pk) and @expose('/submit/<pk>', methods=['POST']) def submit_batch(pk) on PaymentBatchView, each calling the corresponding PaymentsService method. For StandingOrderView add @expose('/pause/<pk>') and @expose('/resume/<pk>'). This pattern is already established in the codebase — just extend it.

### connectivity_config encryption not enforced despite being documented as required

PaymentRail.connectivity_config stores API credentials, endpoint URLs, and API keys in plaintext JSONB. The column comment explicitly says 'values must be encrypted at rest — see pgappforge.plugins.integrations.encryption' but no encryption is applied anywhere. A database read or backup exposure leaks all rail credentials (MPESA API keys, SWIFT credentials, KEPSS certs).

**Benchmarks:** Stripe, Adyen, Checkout.com, Rapyd

**Implementation notes:** In models.py, create a EncryptedJSONB TypeDecorator using pgappforge.plugins.integrations.encryption (or AES-256-GCM via cryptography.fernet if the integrations module is unavailable): class EncryptedJSONB(TypeDecorator): impl = Text; cache_ok = True; def process_bind_param(self, value, dialect): return encrypt_json(value) if value else None; def process_result_value(self, value, dialect): return decrypt_json(value) if value else None. Replace the connectivity_config column type from JSONB to EncryptedJSONB. The encryption key should come from current_app.config['PY_RAIL_SECRET_KEY'] or env var. This is a non-breaking migration if you provide a data migration script that re-encrypts existing rows.

### Reconciliation service absent — no ingest of clearing house settlement files

ReconciliationCompleteEvent is defined with matched_count, unmatched_count, and exceptions fields. No ingest_settlement_file() or reconcile() service method exists. There is no mechanism to consume the daily CBK/KEPSS/PESALINK settlement report and match it against py_payment_order rows. Unmatched items (payments the bank submitted but the clearing house has no record of, or vice versa) are never surfaced. Real-time reconciliation against settlement data is a Tier 4 world-class requirement.

**Benchmarks:** Stripe, Adyen, Checkout.com, Rapyd

**Implementation notes:** Add a new model to models.py: class PaymentReconciliationRun(AuditMixin, Model): __tablename__ = 'py_reconciliation_run'; fields: id (UUID PK), tenant_id (VARCHAR 64), rail_code (VARCHAR 20), settlement_date (DATE NOT NULL), file_reference (VARCHAR 100), status (VARCHAR 20: PENDING | PROCESSING | COMPLETE | FAILED), total_items (INTEGER), matched_count (INTEGER), unmatched_count (INTEGER default 0), exceptions (JSONB — list of {payment_reference, issue}), run_at (TIMESTAMPTZ). Add to services.py: def reconcile_settlement(self, *, rail_code: str, settlement_date: date, settlement_items: list[dict]) -> PaymentReconciliationRun. Each item dict: {payment_reference, amount_cents, cleared_at}. Logic: for each item, look up the PaymentOrder by payment_reference + tenant_id; if found and status is SUBMITTED_TO_SWITCH/PROCESSING, call settle_payment(); if amount mismatch, add to exceptions; if not found in settlement, add as exception. On completion: INSERT PaymentReconciliationRun with counts; emit ReconciliationCompleteEvent.


## Medium Priority Gaps

### No ORM relationships declared — cascade deletes and lazy loading uncontrolled

PaymentOrder has no relationship() to PaymentStatusEvent (history), PaymentBatch (parent), or StandingOrder (origin). PaymentOrder.batch_id has no ForeignKeyConstraint to py_payment_batch. With no relationships, ORM queries require explicit joins, cascade deletes are undefined (deleting a PaymentBatch may orphan orders or fail), and there is no way to eager-load the status event history on a PaymentOrder without a second explicit query.

**Benchmarks:** Stripe, Adyen

---

### Sanctions screening checks only creditor_name; misses account number, BIC, and debtor

_run_sanctions_screen passes only order.creditor_name to the screener. A sanctioned entity operating under a compliant name but a flagged account number or SWIFT BIC is not caught. The debtor is never screened. With no screener configured, sanctions_checked is set True — a false signal that screening actually ran. OFAC/UN/EU sanctions require screening of all parties and identifiers, not just the beneficiary name.

**Benchmarks:** Stripe, Adyen, Rapyd, Paystack

---

### Direct debit mandate lifecycle absent

DIRECT_DEBIT is a valid payment_type but there is no mandate model, no mandate creation, amendment, cancellation, or presentment workflow, and no dispute handling. Direct debit pull-based payments require explicit pre-authorization from the account holder (DDI — Direct Debit Instruction) before any debit can be presented. Without a mandate, any DIRECT_DEBIT payment would be initiated without authorization evidence, violating CBK and ACH Kenya rules.

**Benchmarks:** Stripe, Adyen, Rapyd

---

### Dashboard uses inline render_template_string with no real charts or rail status

PaymentsDashboard.dashboard() uses render_template_string with a 5-item plain HTML list. The view docstring promises 'volume charts, rail status, settlement summary' — none are implemented. The dashboard is a stub that provides no operational value. All world-class payment platforms provide real-time operations dashboards (authorization rate, settlement volume by rail, inflight count, failed orders requiring attention).

**Benchmarks:** Stripe, Adyen, Paystack

---

### PAIN.001 stored as TEXT column in database — unsuitable for production batch sizes

PaymentBatch.payment_file_content is a TEXT column. The model comment acknowledges this is not suitable for production. A 1,000-transaction EFT batch generates ~500KB of XML. A 10,000-transaction batch generates ~5MB. Storing these in a TEXT column bloats the database, makes the py_payment_batch table slow to scan, and prevents streaming. PostgreSQL's maximum TEXT size is 1GB but page bloat degrades performance well before that.

**Benchmarks:** Adyen, Rapyd
